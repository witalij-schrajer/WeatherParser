## Findings

1. **NU1004 for the RID-specific locked restore** (Class A step 1); the user decided to keep the projects RID-neutral.
2. **The tool resolver cache defeated the run isolation** (found on the target with script revision `b7396d3`). `dotnet tool run` resolves local tools through the per-user cache `~/.dotnet/toolResolverCache`, which the script did not isolate.
   - On Debian, the first run's entry pointed to that run's deleted package folder, and `dotnet tool restore` does not replace an entry of the same version. Every later run therefore failed at conversion with exit 80 ("Run dotnet tool restore …"); the first `RunSettingsTamper` runs ended there.
   - On Windows, the entry pointed to the user's global `~/.nuget/packages`, so every earlier Windows run executed the pinned `dotnet-coverage` 18.11.0 from outside the run's isolated folder.
   - Fixed in `660dc7e`: each run and each resume uses its own `DOTNET_CLI_HOME`. Verified on Windows (the cache entry now points into the run's package folder) and in the final ARM64 series. The P1.09 record carries a dated correction.
3. **Relative `-ResumeFrom` path** produced wrong relative runner paths (exit 20); fixed in `d962188` by resolving the directory first.
4. **Line endings and the script identity check:** the collecting and the resuming script are compared with line endings normalized, because Git checks the same commit out with LF on Debian and CRLF on Windows (`core.autocrlf=true`).
5. **`prepare-debian-arm64.sh` stdout:** `dotnet-install.sh` progress reached stdout and broke the `eval` contract; fixed in `24c9fec`. The target runs used only the `export` lines.
6. **`hashes.sha256` of the PowerShell release** is UTF-16LE with a BOM and CRLF line endings; the preparation script converts it before checking.
