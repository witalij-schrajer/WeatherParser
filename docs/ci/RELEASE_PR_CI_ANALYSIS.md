Each job's `gate-result.json` reports the failed rule `Comparison`: "Block coverage 11102/11103 (99.99%) is equal to baseline 11102/11103 (99.99%); a code PR must strictly increase block coverage below 100%." The script stops at the library gate, so the CLI gate is not evaluated; the CLI columns are the counters in the run artifacts, equal on each platform, so the CLI gate would fail the same way.

The cause is the rule, not a defect. Since the release, `develop` changed gated inputs (`Directory.Packages.props` and the library project file, for `1.1.0-dev` and package validation) without library code. Such a change keeps strict improvement unless a recorded baseline reconciliation applies. On `develop` pull request #27 made this change under two reconciliation entries, but those were bound to its own head branch and target (REQ-086 amendment 2) and were removed after its merge, so they do not apply to a release pull request.

### When the gate would pass today

A release always changes the version in the library project, a gated input for both gates, so the normal rule always applies. Below an exact 100% baseline, each gate then passes only if its coverage is strictly above the last release on the platform measured, so a release needs that on all three jobs; an exact 100% baseline accepts an exact 100% result (REQ-086), which neither gate has today. That holds when `develop` has at least one change that strictly improved that gate, and fails when every change since the release was coverage-neutral or reconciled. A library or CLI release therefore passes or fails by content, not by quality: while the gates stay below 100%, a release with nothing but a dependency security update is a sure failure.

### Separate limit: incomparable measurements

An SDK or coverage-tool change on `develop` makes the target and the head incomparable, which fails with exit 85 under every option below. The method of RL-09 A3 for this case is not implemented (no `fromSdk` handling in `tools/` or `scripts/`). It already blocks the updating pull request into `develop`, so that update needs its own decision first, and this analysis leaves it open.

## 4. Options for the gate on a release pull request

Every gate decision on `develop` was made against the then-current `develop`, so a release pull request adds no new change. What its comparison can still catch is a decrease across the whole release, for example from two pull requests that each passed alone but lower coverage when combined.

| Option | Rule | Effect | Cost |
|---|---|---|---|
| **A: defined release rule (recommended)** | Amend REQ-086: a pull request from `develop` of this repository into `master` may retain equal coverage on both gates; a decrease still fails; comparability, measurement, minimum and exact-100% rules are unchanged; the gate result names the rule and keeps the counters | Every release gets a real result without manual steps; a decrease stays visible as a failure | A rule change plus test-first code: a new category in the coverage runner, the base branch passed from `ci.yml` through `ci-local.ps1`, and tests. Manual and local runs supply no base branch unless given, so the rule does not apply to them by default |
| B: recorded reconciliation per release | Keep REQ-086; for each release the user approves two `coverage-reconciliation.json` entries (library, CLI) with the target `master` tip and head `develop` | No code change; the user decides each time | Three pull requests per release (entries, release, cleanup). The entries need the release pull request's number, so that pull request must exist first and fails once. `check-promotion.ps1` treats `coverage-reconciliation.json` as a build input, so the entries must be merged before the release candidate is built |
| C: minimum only on release pull requests | Skip the comparison; only the 80% minimum applies | Simple | A release-wide decrease goes unnoticed, down to the minimum. Not recommended |
| D: keep the rule | Nothing changes | Releases with strict improvement pass; others stay red, as #26 was, and the user merges past a failed check (the ruleset requires no status check) | Red release pull requests carry no information about whether something is wrong. Not recommended |

**Recommendation: A.** It matches the existing pattern of the amendments (equal accepted, decrease fails), needs no per-release ceremony, and does not disturb the promotion check. A narrows no other rule: pull requests into `develop` keep the existing REQ-086 rules and exceptions.
