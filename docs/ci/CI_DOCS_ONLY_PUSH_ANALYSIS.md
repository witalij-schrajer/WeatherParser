# Documentation-only pushes hiding CI results: analysis

Status: the user chose option A on 2026-11-04 (section 5); it is implemented (section 6). Sections 1 to 4 describe the state before that change.

Written by the orchestrating agent (documentation is not generated by qwen, user decision dated 2026-10-24). Evidence dated 2026-11-04, from pull request #29.

## 1. Summary

A documentation-only push to a pull request with code changes shows the CI jobs as skipped and the checks as passed, whatever the state of the jobs that test the code. On pull request #29 the box said "All checks have passed" while the code jobs were still running. The cause is that `changes` judges a push by its own commits only. Judging the whole pull request on every event closes the gap, at the cost of about six minutes of CI for such a push. This changes one sentence of the user decision dated 2026-10-28.

## 2. What happened on pull request #29

Head `4604f1c` changed one Markdown file on top of `74d116c`. Two CI runs started for it at the same moment:

| Run | Trigger | Range judged | Jobs |
|---|---|---|---|
| [41735220388](https://github.com/witalij-schrajer/WeatherParser/actions/runs/41735220388) | push | `74d116c..4604f1c` (1 Markdown file) | all three skipped |
| [41735220070](https://github.com/witalij-schrajer/WeatherParser/actions/runs/41735220070) | ready for review | the whole pull request | all three ran, finished about five minutes later, passed |

The pull request page showed the skipped jobs and "All checks have passed" while `windows-x64` had not passed on any run. All jobs later passed, so no defect was missed; the display was wrong for those minutes.

## 3. The gap

- **Same head.** Runs for one commit share job names, and the page showed the skipped jobs while the real ones of the other run were still in progress, as section 2 shows.
- **New head.** `ci.yml` starts on `synchronize` and, for such a push, judges only `before..head`. If a code run on the previous head failed, a documentation-only push on top gives the new head only skipped jobs. No failure is attached to it, so the pull request shows green over a real failure. This is traced from the workflow, not observed: pull request #29 had no failing run.

The second case is the serious one. The repository has no required status checks (the ruleset "Gitflow - master and develop"), so the box is what the user reads before merging, and every code pull request here ends with a Markdown recording commit.

## 4. Options

| Option | Change | Effect | Cost |
|---|---|---|---|
| **A: judge the whole pull request on every event (recommended)** | `changes` always uses `base...head`; the `before..head` branch goes | Every head of a code pull request has real results; a documentation-only pull request still skips the jobs | One more full run (about six minutes on the runs of pull request #29) for each documentation-only push to a code pull request. Changes "A push is judged by its own commits" in the 2026-10-28 decision |
| B: summary job | Keep the skip; add a job that looks up earlier runs of the pull request through the API and fails while one is unfinished or failed | No extra CI minutes | Needs `actions: read`, handling of runs still in progress, and more workflow logic with no test harness. The skipped jobs still appear as skipped. Not recommended |
| C: keep it, document it | Nothing changes in `ci.yml`; CONTRIBUTING.md says to read the run page | No cost | Relies on the reader, and the box stays misleading. Not recommended |

**Recommendation: A.** It removes code instead of adding it, and it keeps the purpose of the 2026-10-28 decision, which is no CI for documentation-only changes: those pull requests still skip. The repository is public, so the extra runs use the free hosted minutes for public repositories.

Option A leaves two things as they are: a push and a ready-for-review event for the same head still give two runs, and `cancel-in-progress` stays off. Both could change later, but neither is needed for this fix.

## 5. Decision

The user chose option A on 2026-11-04 ("Option A, whole PR", the answer to the question on pull request #30). It amends one sentence of the 2026-10-28 decision in AGENTS.md; documentation-only pull requests still skip the jobs.
