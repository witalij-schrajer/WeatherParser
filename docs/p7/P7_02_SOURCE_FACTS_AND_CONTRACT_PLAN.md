## 1. Goal and Scope
Goal: record the MOSMIX source facts from official DWD documents and the actual published files, settle the technical questions the phase plan leaves to this step (archive CRC behavior, request bound, retained-size bounds, timing), write the contract decisions MF-01 to MF-18 in `docs/p7/P7_FORECAST_CONTRACT.md`, have them reviewed by Codex and approved by the user, and reconcile the phase plan and the step plans P7.03 to P7.12 with the approved contract.
In scope: one documented retrieval of each source (schema, element definitions, product and directory descriptions, the procedure description with the update cycles, one MOSMIX_L per-location file, one MOSMIX_S all-stations file, the DWD terms of use); the structural facts of both file forms; the manual derivation of the source structures from the schema (REQ-112); the element table with units, reference periods and pressure reduction; ID grammars; file sizes; the CRC-32 behavior of `ZipArchiveEntry` in the pinned runtime; timing and memory probes of the MOSMIX_S download and stream parse; the contract record with source register; Codex review loop; user approval; plan reconciliation.
Out of scope with owner: production code and tests → P7.03 onwards; any change to the P4 selection contract (only a recorded amendment proposal for the user, MF-18).

## 5. Procedure
No slice changes behavior, so there is no Red step. The orchestrating agent writes all text (documentation is not generated by qwen) and verifies every fact.

### S1 Source facts
- One GET each with a descriptive User-Agent and no retries; status, content type, bytes, SHA-256, UTC time and, for the MOSMIX_S all-stations file, the download duration recorded (the only MOSMIX_S download of this step; S3 replays this exact file): `pointforecast_dwd_extension_V1_0.xsd` (revision and checksum compared with SC-20), `MetElementDefinition.xml`, the MOSMIX product description and directory pages, the procedure description cited in AGENTS.md (cycles, section 2.1.3/table 2.1), one `MOSMIX_L_LATEST_<id>.kmz`, one `MOSMIX_S_LATEST_240.kmz`, the DWD terms of use.
- Schema derivation (REQ-112): every element, attribute and type of the extension schema the parsers rely on, with namespace, cardinality and the KML elements around it, recorded as a table; additional KML structures verified against the published files; differences from SC-20 recorded.
- Element table for every element MF-10 and MF-11 consider: definition text, unit, reference period ("during the last hour" and similar), pressure reduction of `PPPP`, presence in each product (S: 40 elements per P4; L: 114 per P4, rechecked).
- File facts: encoding, issue time form, timeline length and spacing, coordinates form, `kml:description` content, missing-token form, member names, compressed and uncompressed sizes, placemark count; MOSMIX ID grammars of both products from the catalog and the files (MF-03).
- Source conditions: the DWD terms of use and attribution wording (MF-16).

### S2 Archive integrity check
- Whether the pinned .NET 10 runtime's `ZipArchiveEntry.Open()` read stream verifies the entry CRC-32: the runtime source at the pinned version read and cited, and a local probe (outside the repository) with a synthetic archive whose stored member is changed in one digit while staying valid XML; the result decides the CRC option of section 3.

### S3 Timing and memory probes
- A probe outside the repository replays the MOSMIX_S file retrieved in S1 from disk (no new download; its SHA-256 checked against the S1 value before each run and, on the NanoPi R76S, after the transfer on both sides): time to stream the unpacked member to its end with `XmlReader` under the SC-22 settings, and the absolute peak working set of the probe process (`Process.PeakWorkingSet64` at its end, the same metric P7.11 verifies), on Windows and (with authorization) on the NanoPi R76S; the MF-07 memory threshold is stated as such an absolute process peak; the S1 download duration and the replay times feed the request bound and deadline defaults of MF-05, and the observed timeline length and element counts the retained-size bounds of MF-07, all from the same run of `LATEST`. Any additional network measurement (for example a download on the NanoPi R76S) needs its own explicit request budget authorized by the user and is recorded separately with its own SHA-256.

### S4 Contract draft and Codex loop
- MF-01 to MF-18 written with options, recommendation and the verified facts, each row traced to its T-P7 IDs; Codex five-angle review read-only, rounds until 0 findings or the tenth round; every finding verified and either fixed or rejected with reason; every round's output and finding count recorded in the contract.

### S5 User approval
- The user approves or amends each MF row; the approval wording and date recorded; rejected options kept as rejected alternatives; additive export decisions (MF-09, MF-11) are numbered as new C decisions in P7.03, citing the MF row.

### S6 Reconciliation
- The phase plan and step plans P7.03 to P7.12 updated where the approved contract differs; "Proposed" labels for approved items removed; Codex review of the reconciliation; checkpoint commit on the user's request.

## 8. Risks and Limitations
- (a) The schema revision or checksum differs from SC-20 — recorded; the new revision is evaluated and the difference presented to the user before approval
- (b) An element definition does not state its period or reduction — the element is not mapped to an interval or pressure field without the user's decision (REQ-055, REQ-054)
- (c) The download duration from one Windows retrieval is a single sample of a variable network; the MF-05 defaults include a recorded margin and P7.11 re-measures
- (d) The MOSMIX_S stream takes longer on the NanoPi R76S than a useful deadline allows — recorded; the user decides between a longer bound and a documented limitation
- (e) A source is unreachable — recorded; the user decides whether to wait
