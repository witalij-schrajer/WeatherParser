## 2. Goal, binding scope and exclusions

Goal: a generic, provider-independent MQTT message serializer in the library that turns one supported export root into one message with a consumer-configured topic, the JSON payload of the existing JSON serializer, QoS and retain, without any broker connection or credentials; and the acceptance of the complete library (station selection, DWD observations, OsthessenWetter observations, MOSMIX_L and MOSMIX_S forecasts, export entities, JSON, XML, XSD, MQTT serializer and DI) through actual package consumption, as the gate for P3.

In scope:
- the public MQTT message contract of REQ-015: a message entity with topic, payload, QoS and retain; a serializer interface and its implementation; no MQTT client library, no broker connection, no credentials (REQ-012, REQ-015, REQ-060 library part)
- the JSON payload produced by the existing `IJsonExportSerializer` from the same export entities, byte-identical to the JSON export of the same root (REQ-050, REQ-069, REQ-075)
- consumer-supplied topic templates and their mapping to message types, with placeholders filled from the root (REQ-015, REQ-061); no hardcoded `haus/weather/...` path in library behavior
- validation of templates and resolved topics without broker access: missing mappings, unknown and unresolved placeholders, placeholder values that would inject topic levels or wildcards, and invalid publish topics fail with defined error IDs (REQ-015)
- the agreed QoS and retain semantics as configurable message properties (REQ-062: observations and forecast runs QoS 1 retained, station lists QoS 1 not retained); one complete forecast run per message, distinct topics per product and location so that retained state is never replaced across products (REQ-061, REQ-062, C-68)
- separation of observations and forecasts on the message level: a forecast run is only ever a forecast message and never carries `measured_at` (REQ-050, REQ-105)
- DI registration in `AddWeatherParsing` with consumer-supplied topic configuration (REQ-016, C-107, C-108)
- the complete library integration through the same-run package: every parser and service resolved from one consumer container, every source run offline with fake HTTP, every result serialized as JSON, as schema-valid XML and as an MQTT message (DEVELOPMENT_PLAN.md P8 acceptance, REQ-012, REQ-013, REQ-016)
- the inherited "DI under load" item, README section "MQTT serializer (library)", integrated coverage and platform verification, acceptance of P8 and of the complete library, P3 handoff

Out of scope with owner:
- broker transport, connection, TLS, authentication, credentials, acknowledgment handling, timeouts and retries of publication, partial-failure summaries and exit codes (REQ-060, REQ-063, REQ-072 CLI part) → P3 example transport
- CLI options, configuration format and location, environment variables, `--Output`, `--OutputFile` (REQ-064 to REQ-066, REQ-073) → P3
- publication of any OsthessenWetter value over MQTT or otherwise (OW-14) → not before the user records the operator's consent or other clarified conditions; P8 serializes synthetic datasets only and publishes nothing
- MQTT error collection (REQ-072 "future feature") → not planned
- export contract changes: P8 adds no export member; the MQTT payload uses the frozen v1 roots unchanged (C-03, C-105)
- package ID, feed and publication → P9

Decisions are recorded in `docs/p8/P8_MQTT_CONTRACT.md` (decision IDs `MQ-01` to `MQ-15`) in P8.02, reviewed by Codex read-only (up to 10 rounds) and approved by the user before the affected Red test. | ID | Decision | Options / recommendation | Decided by | Blocks |

| MQ-01 | Protocol facts | Record in P8.02 from both specifications: topic names are UTF-8 strings of 1 to 65 535 bytes, without U+0000; `+` and `#` are not permitted in a topic name used for publication; `/` separates levels and empty levels are permitted; topics beginning with `$` are reserved for server use; the maximum remaining length of a packet is 268 435 455 bytes; QoS values 0, 1, 2; the retain flag. | MQ-04 | Template grammar and placeholders | Templates are literal text with placeholders `{name}`; literal `{` and `}` are invalid (no escape syntax); placeholders per message type, filled only from the root: `observation`: `{source}`, `{provider}`, `{station_id}`; `forecast`: `{source}`, `{provider}`, `{mosmix_id}`, `{product}` (wire form `MOSMIX_L` / `MOSMIX_S`); station lists: `{provider}` from the list `source`. An unknown placeholder name, or a placeholder not available for the template's message type, fails at options validation (`MQTT-OPTIONS-INVALID`), never at serialization. Option B: consumer-supplied per-call variables for further topic parts (rejected for now: no recorded consumer need; the configurable station and source parts of REQ-015 are covered by the placeholders) | User (P8.02) | P8.03, P8.04 |
| MQ-05 | Topic uniqueness rules | So that retained state of one source, product or location is never replaced by another (REQ-061, REQ-062), two rules guarantee distinct resolved topics. Within one message type: an `observation` template must contain `{source}` as a whole topic level, or `{provider}` and `{station_id}` each as a whole topic level; a `forecast` template must contain `{source}` as a whole topic level, or `{product}` and `{mosmix_id}` each as a whole topic level. Placeholder values never contain `/` (MQ-06), so a whole-level placeholder reproduces its value exactly in its level and cannot run into neighboring text; a distinguishing placeholder that shares a level with literal text or other placeholders does not count (for example `o/{station_id}{source}{provider}` resolves to `o/abc:abc` both for provider `bc`, station `a` and for provider `c`, station `ab`). Further placeholders and literal text may appear in other levels. Across message types: the literal prefix of each template (the text before its first placeholder, or the whole template when it has none) must diverge from the literal prefix of every other mapped template at a character position inside both prefixes, so that neither prefix is a prefix of the other; the resolved topics of two message types then differ at a fixed position whatever the placeholder values (for example `haus/weather/measurements/` and `haus/weather/forecasts/` diverge; `weather/{source}` and `weather/{provider}:{mosmix_id}` share the prefix `weather/` and are rejected, because they can resolve to the same topic). Violations → `MQTT-OPTIONS-INVALID`. A: these validation rules (recommended) / B: placeholder presence and unequal template text only (rejected: different templates can resolve to the same topic) / C: no rule, README guidance only (rejected: retained state could be overwritten silently) | User (P8.02) | P8.04 |
| MQ-06 | Placeholder value safety | A value inserted into a topic must not change its structure (REQ-015): an empty value, or a value containing `/`, `+`, `#`, U+0000, a control character (U+0001 to U+001F, U+007F to U+009F) or an unpaired surrogate fails with `MQTT-PLACEHOLDER-VALUE-INVALID`; no escaping or substitution, because a substituted value could collide with another source's topic. The existing grammars (C-50, OW-03 slug, MF-03, DWD five digits) do not produce such values; the check guards consumer-built roots | User (P8.02) | P8.03, P8.05 |
| MQ-07 | Resolved-topic validation | After substitution: non-empty; at most 65 535 UTF-8 bytes; no `+`, `#`, U+0000; not starting with `$`; empty levels (`a//b`, a leading or trailing `/`): A: rejected (recommended: in this project they arise only from configuration mistakes) / B: permitted as by the specification; violations → `MQTT-TOPIC-INVALID`. At options validation the template is checked template-aware, not fragment by fragment: the characters of every literal part are checked (no `+`, `#`, U+0000 or control characters), a leading `$` only when the template starts with a literal, and empty levels only where they arise whatever the placeholder values: `//` inside a literal part, a template starting or ending with `/`; a literal part that ends or starts with `/` next to a placeholder (as in `haus/weather/measurements/{source}/state`) is valid, because placeholder values are never empty (MQ-06); the complete-topic rules apply to the resolved topic only | User (P8.02) | P8.03, P8.04 |
| MQ-08 | QoS and retain | Per mapping: A: QoS and retain default to REQ-062 (observation and forecast: QoS 1, retained; station lists: QoS 1, not retained) and may be overridden per mapping (recommended: the agreed semantics without hidden coupling to the CLI) / B: QoS and retain required in every mapping without defaults / C: fixed by the library (rejected: REQ-015 "consumers supply" and generic use). QoS outside 0 to 2 → `MQTT-OPTIONS-INVALID` | User (P8.02) | P8.04 |
| MQ-09 | Options and registration | A: a consumer-registered `MqttTopicOptions` (Proposed: `Mappings` per message type with `TopicTemplate`, `QualityOfService`, `Retain`; `MaxPayloadBytes`), validated on first resolution with `MQTT-OPTIONS-INVALID` (the MF-04 pattern); an empty instance is valid and makes every serialization fail with `MQTT-MAPPING-MISSING`, so JSON/XML-only consumers register `new MqttTopicOptions()` (recommended: REQ-016 "wiring … topic settings", C-107, C-108 unchanged) / B: the configuration passed on every call (rejected: no DI wiring of topic settings, REQ-016) / C: a factory registration that tolerates missing options (rejected: C-107 forbids factories) | User (P8.02) | P8.04, P8.07 |
| MQ-10 | OsthessenWetter values | The serializer is generic and accepts every valid `ObservationDataset`, also of provider `osthessenwetter` (REQ-015: no provider logic).
